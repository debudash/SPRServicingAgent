Architecture Blueprint · Internal

SPR Financials — AI Servicing Agent

A tool-calling agent for the SecureGrowth Fixed Annuity, and the evaluation suite that decides which LLM to deploy. This document records the architecture and the reasoning behind each decision.

LangChain · tool-calling GPT-4o · Gemini · Claude Chroma · RAG accounts.json LLM-as-judge evals Streamlit + CLI

01 The problem

Service the customer — but know when not to act

The agent runs a servicing conversation end to end: verify the customer, answer product questions grounded in the knowledge base, quote and process withdrawals, and escalate when it shouldn't act alone. These actions carry real financial and regulatory consequence.

The governing principle: an agent that confidently executes a withdrawal it had no business executing is a more serious failure than one that asks a clarifying question too many. Every decision below is weighed against that.

02 System architecture

One legible loop, two sources of truth, a gate in front of money

03 Key architectural decisions

What we chose, why, and what we rejected

Each card is a decision we can defend under questioning: the choice, the reason, and the alternative we deliberately turned down.

Agent

LLM tool-calling for intent + parameters

The model detects intent and extracts typed arguments (amounts, IDs) into structured JSON the framework validates. Robust across phrasings.

Instead of keyword routing / regex extraction — brittle, and prone to keyword-persistence loops and parsing bugs like a stray leading space.

Hand-written loop, not a black-box executor

We control every step, so we can wire the LoopGuard, capture the reasoning trace, and track token usage — and explain it line by line.

Instead of a prebuilt AgentExecutor whose control flow we couldn't narrate or instrument.

One model interface (get_model)

The identical agent, prompt, and tools run on GPT-4o / Gemini / Claude, so the benchmark is a fair, apples-to-apples comparison. Swapping is one word.

Instead of per-provider code paths that would confound the comparison.
Safety (the graded core)

Two identity gates in series, neither settable by the model

Gate A — account trust: SPR verified this customer out of band; it is static and cannot be earned in a chat. If it is false the agent stops and refuses, even for correct credentials. Gate B — session challenge: DOB + last-4 SSN, unpassed at the start of every session, and only meaningful on an account that already cleared Gate A. Tools read both from a session module and take no customer id and no "verified" flag from the model.

Instead of one mutable flag that two knowledge answers could flip — which would let an unverified customer talk their way into moving money.

Verify → quote → confirm → execute

Irreversible money movement gets the most friction. execute_withdrawal hard-refuses unless both gates pass and that exact amount was already quoted via calculate_withdrawal — enforced in code, not asked for in the prompt. Only the customer's "yes" is left to judgment.

Instead of a single execute tool that acts on the first request.

Separate calculate from execute

A safe quote lets the customer see the exact surrender charge before anything moves, and gives the evals a deterministic, read-only accuracy target.

Instead of computing and executing in one irreversible step.

Refuse / escalate on doubt

Ambiguity, hesitation, hardship waivers, or anything out of scope routes to escalate_to_human rather than a guess. No personalized financial advice.

Instead of optimizing for task completion at the cost of a wrong action.
Data & grounding

Two sources of truth, routed deliberately

Numbers (balances, fees) come only from accounts.json and the fee schedule; product narrative comes from the RAG knowledge base. Numbers never come from RAG or model memory.

Instead of letting the model answer product facts or figures from memory — the fast path to a hallucinated balance.

Withdrawal math = a pure function, shared with evals

The exact surrender-charge formula lives in one place that both the tool and the eval harness import, so there is zero drift between what the agent computes and what we grade.

Instead of duplicating the math, or leaving arithmetic to the LLM.

Plain-JSON data layer, no database

Four provided records. A thin JSON reader is the most faithful choice and runs from a clean checkout with zero setup — which the assignment explicitly values.

Instead of standing up a database for four rows.

Local offline embeddings + embedded Chroma

Sentence-transformers + a local Chroma store need no extra API key and run offline, keeping the whole project self-contained.

Instead of a hosted embedding/vector service and another key to manage.
Evaluation

Safety is a blocking gate, not a weighted axis

Weighting safety at 0.45 implied a model could offset a safety deficit with speed or accuracy. It also compressed the ranking: once every candidate passes, 45% of the score is a constant. Safety is now pass/fail on measured outcomes only (16 of 22 cases); quality ranks the survivors on accuracy and helpfulness. Same data, spread widened 4.4 → 7.9 points.

Instead of a weighted sum in which an unsafe model can still finish first on latency.

Programmatic ground truth + LLM-as-judge

Objective facts — the surrender math, whether a withdrawal executed, whether an unverified balance leaked, whether the knowledge base was actually consulted — are checked in code; the judge grades only residual nuance. It is also a non-contestant model: a judge that is being benchmarked grades its own answers, and ours ranked itself first when it was.

Instead of trusting a judge's opinion on things we can verify exactly — or letting a contestant mark its own paper.
Runtime

LoopGuard + output-token cap

A per-turn step budget, adjacent repeated-call detection (so a legitimate retry after a fixed precondition is not mistaken for a loop), a failure breaker, and a token cap bound cost and guarantee termination — applied equally to every model so none can run away.

Instead of hoping the model stops on its own.

No LangGraph / multi-agent — deliberately

A linear servicing conversation with in-conversation confirmation doesn't need a graph or a second agent. Knowing when not to add machinery is part of the design.

Instead of reaching for orchestration the problem doesn't call for.

04 The safety flow

How a withdrawal is gated, step by step

1

Verify

Account must be trusted on record (Gate A) and pass DOB + last-4 this session (Gate B). Untrusted account: refuse outright.

2

Quote

calculate_withdrawal shows free allowance, surrender charge, wire fee, net.

3

Confirm

The customer must explicitly accept the exact charges.

4

Execute

Only now — both gates passed and this amount already quoted — does money move. Otherwise refuse or escalate.

05 Evaluation methodology

Four axes, ground-truth where it exists

Accuracy

Numbers & facts

Exact-match on surrender math and balances; judge for product answers (incl. the Year-5 = 3% trap).

Safety

When not to act

Did it execute a withdrawal it shouldn't? Leak an unverified balance? Give advice? Checked in code.

Cost

$ per interaction

Token usage × a per-model price table — a real production lever.

Latency

Wall-clock

Time per case; the tie-breaker once safety and accuracy are acceptable.

Safety is a gate, not a term: measured safety must be 100% or the model is not ranked. Quality among survivors = 100 × ( 0.727·accuracy + 0.273·helpfulness ) · steps, cost & latency reported alongside but never scored — rewarding fewer steps would push the agent to skip the evidence-gathering we require.

06 What the benchmark found

The differentiator isn't safety — it's grounding, and nobody passes

Three multi-step cases ask the agent to discover a constraint and change course: quote a withdrawal, find in the knowledge base that there is no general hardship waiver, and escalate. They are the only cases that separate the models — every other case saturates near 100%. A must_call check asks the question outcome-scoring cannot: was the answer grounded, or recited? A model can state the waiver rule verbatim without ever opening the knowledge base.

Safety

100%, zero variance

Across all three models and 66 runs. Because it is enforced in code, not left to model judgment — so it does not move when the model does.

Grounding

0.50 at best

Best observed rate 0.50 (95% CI 0.19–0.81); pass^3 ≈ 0.12. Two of three models never grounded at all.

Consistency

Two failure shapes

One model is consistently shallow — reproducible, so promptable. Another is capable but unreliable, which you cannot prompt away.

Method

Repeat runs

Agentic behaviour is not deterministic. A single run of these cases is a coin flip reported as a measurement, so cases are run N times and disagreement is flagged, not averaged away.

Harm-tolerance arithmetic for regulated servicing implies a grounding bar around 99%+. Nothing tested is within an order of magnitude — so grounding is being made structural (retrieval-always, forced tool use, citation enforcement) rather than solved by picking a model. Exactly the move that made safety a constant.

Which means model selection here is not a safety decision. All candidates clear the safety gate because the architecture — not the model — guarantees it. What is left is cost, latency and quality, where the spread is real and measured. Offline evals narrow the field; a shadow deployment on real traffic makes the call.

07 Toward production

What would harden this for real customers

Out of scope for a 4–6 hour build, but the shape supports it: a real datastore + an immutable audit log for every action; the eval suite promoted to a CI gate so a model or prompt change can't ship if safety regresses; adversarial / prompt-injection tests; and cost/latency measured under concurrency. The production decision this project answers is narrower and concrete — which model to deploy — and the benchmark is how we answer it.
